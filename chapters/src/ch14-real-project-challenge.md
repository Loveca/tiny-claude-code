# ch14: Real Project Challenge

> 最终验收不是又写一个模块，而是用自己造的 agent 修真实问题。

## 本章目标

ch14 不引入新的 agent 机制。它提供几个真实感更强的挑战项目，让你验证前面十四章构建出来的能力：读代码、运行测试、定位错误、编辑文件、复跑验证、总结结果。

## 问题：单元测试通过不代表 agent 真能工作

前面每章都有测试，但测试验证的是单个机制是否按预期运行。真实 coding agent 面对的是组合问题：它要读懂任务、选择工具、处理失败、修改文件、再次验证，还要在上下文变长时保持方向。

一个真实修复过程通常长这样：

```text
read failing test
   |
run command
   |
inspect traceback
   |
read source
   |
edit source
   |
run tests again
   |
summarize result
```

任何一环弱，最终体验都会掉下来。本章的价值就是把这些机制放到同一个场景里验收。

## 解决方案：用渐进挑战暴露真实短板

三个挑战按风险递增：

1. `buggy-python-project`：范围小，反馈明确，适合验证最小修 bug 闭环。
2. `tiny-web-app`：涉及多文件和功能添加，适合验证计划、编辑和测试。
3. 自己的项目：噪声最多，最能暴露权限、上下文、记忆和工具覆盖不足。

不要一开始就拿大型项目测试。先用小挑战确认 agent 的基本工作流，再扩大任务边界。

## 挑战真正考什么

前面章节分别实现了 loop、工具、权限、上下文、Todo、Subagent 和后台任务。真实项目挑战的目的，是把这些能力放回同一个反馈闭环里：观察问题，定位原因，编辑文件，运行验证，根据结果继续迭代，最后给用户一个可复查的总结。

这和普通“让模型回答问题”不同。coding agent 的关键能力不是一次说对，而是能在外部环境里校正自己。测试失败、命令报错、文件不存在、用户插话，都是新的观察；agent 应该把它们纳入循环，而不是假装原计划仍然成立。

做挑战时要刻意缩小任务边界。先让 agent 修一个小 bug，再让它处理一个小 Web App，最后才尝试自己的项目。边界越清楚，越容易看出当前 agent 是缺工具、缺上下文管理，还是缺错误恢复。

## 观察维度

做挑战时不要只看“最后有没有成功”。更有价值的是观察 agent 如何失败：

| 现象 | 可能原因 |
| --- | --- |
| 不知道先看什么文件 | 工具选择或项目理解不足 |
| 一直重复跑同一条命令 | Todo 或状态更新不足 |
| 覆盖了不该改的文件 | 权限和路径边界不足 |
| 忘记前面验证结果 | 上下文/compact 摘要不足 |
| 子任务输出淹没主线 | 需要 subagent 或更好的摘要 |

这张表也能指导后续扩展：不要抽象地说“agent 不够聪明”，而要定位是哪一层 harness 能力不足。

## 挑战 1：Buggy Python Project

目录：

```text
examples/buggy-python-project/
```

运行：

```bash
python -m pytest examples/buggy-python-project
```

这个项目包含三个失败点：

- 折扣计算把百分比当成固定金额。
- 购物车总价忽略 `quantity`。
- 免运费门槛没有包含边界值。

让 agent 做的任务：

```text
运行 examples/buggy-python-project 的测试，根据失败修复实现，并复跑测试。
```

## 挑战 2：Tiny Web App

目录：

```text
examples/tiny-web-app/
```

运行：

```bash
python -m pytest examples/tiny-web-app
```

这个项目是一个无依赖 route table。测试要求新增 `/about` 路由。

让 agent 做的任务：

```text
修复 examples/tiny-web-app，让 /about 返回 about tiny app。
```

## 挑战 3：自己的项目

前两个挑战是受控练习。真正的验收是让 agent 在你自己的项目里完成一个小任务，例如：

- 修一个失败测试。
- 补一段 README。
- 搜索 TODO 并给出整理。
- 给一个函数补测试。

任务要足够小，方便你判断 agent 是否真的完成。

## 挑战路线

### 第一步：先让 agent 观察失败

不要直接要求它改代码。先让它运行测试或打开错误输出，确认它能把失败变成下一步观察。

### 第二步：限制修改范围

告诉 agent 只修相关文件，避免它在不确定时大范围重写。真实项目里，改动范围越小，越容易审查。

### 第三步：每次修改后验证

coding agent 的价值在反馈闭环。一次修改后必须运行相关测试，而不是只给自然语言解释。

### 第四步：让 agent 总结证据

最后的总结应该包含改了什么、为什么改、跑了什么验证、还剩什么风险。

## 常见失败模式

### 只读 README 不读测试

很多 bug 的真实规格在测试里。agent 如果只读说明文档，容易修错方向。

### 一次性改太多

大补丁会让错误定位更困难。挑战里应该鼓励小步修改和频繁验证。

### 测试失败后继续解释成功

如果验证失败，agent 应该回到观察和修复，而不是把失败包装成完成。
